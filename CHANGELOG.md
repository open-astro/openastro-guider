## [Unreleased]

### Added
- `restore_calibration` JSON-RPC method (#102): puts back the last calibration saved in the profile, so a client can keep guiding after a forced recalibration fails. `guide` with `recalibrate: true` erases the mount's calibration before it calibrates, and a failed run left the mount uncalibrated with no way back over the API. A failed calibration also leaves its `guide` request waiting for it while the guider keeps looping, so the next `guide` was refused as in progress; `restore_calibration` ends that request first (its `SettleDone` has `Status` 1, `Error` "calibration failed; saved calibration restored" and `TotalFrames`/`DroppedFrames` 0, and the sticky-lock setting the calibration forced on is put back), so a client can go `CalibrationFailed` → `restore_calibration` → `guide` without `stop_capture`. The result is `true` when the calibration was restored and every mount (with an AO, the AO and the mount) is calibrated; `false` when some mount has no saved calibration, in which case nothing is changed (no partial AO restore, the waiting request is not ended), or when the restored calibration is not usable with the current Dec guide mode (an RA-only calibration with Dec guide mode Auto, North or South; `get_calibrated` reports the same). Refused (error 1) while calibrating or guiding, while the mount or AO is not connected, and while a guide or dither request is in progress that is not waiting on a calibration. The decision is in the wx-free `src/restore_calibration.cpp`, tested by `test_restore_calibration`.
- `scripts/fake_alpaca_camera.py` can reproduce RA slews and larger star fields without hardware (#98, #99): `--slew-seconds` makes `slewtocoordinatesasync` take time and read `slewing` meanwhile, `--slew-rotates` turns the field about `--pole` with the scope's RA, and `--slew-smear` dims the stars on frames exposed during a slew; `--size`, `--stars`, `--star-seed` and `--imagebytes` give larger, denser fields, and the `/fake/shift` and `/fake/decoy` controls move the whole field or add sensor-fixed stars.
- `MoveTime` in the `GuideStep` event (#119): the milliseconds the guider spent sending the step's guide pulses (RA, then Dec) and waiting for the mount to report them complete, measured in `Mount::MoveOffset`. The next exposure starts only after a mount guide step, so this is the dead time each correction adds to the guide cycle (on RC51, a HAE29C through AlpacaBridge, about the pulse plus the driver's 500 ms `IsPulseGuiding` tail per axis). Absent for AO steps; the guide log CSV is unchanged. The debug log gains one `guide step move time` line per step and a `PulseGuide call took N ms` line per Alpaca pulse. The guide loop itself is unchanged: moves and exposures still run one after the other, and RA before Dec, as in PHD2.
- Closed-loop tests of the calibration (`test_closed_loop_calibration`, #142), with no change to the guider. A simulated mount and guide camera (camera angle, Dec mirror, RA motion shrinking with cos(Dec), Dec backlash, non-orthogonal axes, seeded centroid noise) is pulsed by an exact copy of `Scope`'s calibration state machine, frame by frame as the guider runs it, and the tests pin what it does today: the measured angles and rates over camera angles and mirrored Dec, step counts, the 61-pulse failures, backlash clearing, DEC_NONE, recentering, the South nudge, guide parity, the mount reads, a clear mid-run, and the high-Dec behaviour of #141 (at the audit profile, Dec 75° takes 46 RA steps and Dec 79° and above fail "star did not move enough"). They are the baseline for moving the calibration out of `Scope` into a wx-free, testable module.
- Characterization tests of the default guide algorithms (`test_guide_algorithm_kernels`, #142), with no change to the guider: Hysteresis on RA and ResistSwitch on Dec, run through an exact copy of their production `result()`, `reset()` and setters. They pin what the guider does today, including what the old formula copies in `test_guide_algorithm_math` left out: ResistSwitch's overshoot veto (a reversal smaller than the fast-switch threshold is not corrected while the history still points the other way) and its "not getting worse" check, under which an error on the other side that holds steady below 3 × minMove is not corrected until it grows. They are the baseline for moving the algorithms' math into a wx-free, testable kernel.
- An RMS baseline for the default guiding chain (`test_guiding_rms_baseline`, #142), with no change to the guider. A seeded simulation guides a star with sinusoidal periodic error (480 s, ±10"), RA and Dec drift and 0.5" seeing, at a 2.5 s cadence of 2 s exposures, through the production camera-to-mount transform, the Hysteresis (RA) and ResistSwitch (Dec) kernels with their defaults, and the pulse planning. Guided, the error an imaging camera would see is 0.78" RMS against 19.9" unguided; the test pins that baseline in a ±11 % band that a detuned default leaves, checks it holds across seeds (the baseline was measured in a -O0 and a -O3 build, which agree), and checks that a calibration flipped by 180° on either axis makes guiding diverge.
- How a guide correction becomes mount pulses extracted into a wx-free `src/guide_move_plan.{h,cpp}` (`guide_move_plan` namespace) and covered by `test_guide_move_plan` (#142), ahead of the #115 equipment refactors that move this code. `Mount::MoveOffset` now gets each axis's direction and pulse from `PlanOffset` (+x West, +y South, `ROUND(fabs(distance / rate))`), and `Scope::MoveAxis` gets the guiding-disabled refusal, the Dec guide mode filter, the max RA/Dec duration clamp and the limit-reached count from `PlanAxis`; both keep their Debug lines, the limit alert, the backlash compensation and the pulse itself, so guiding is unchanged. `Mount::SetCalibration`'s axis-orthogonality error is now `calibration_transform::YAngleError`. One edge is now defined: a pulse computed with an RA or Dec rate of 0 cast an infinite or NaN value to `int`, which is undefined behaviour; it now gives `INT_MAX` (a guide step is then clamped to the max duration) or 0 for 0 / 0, the values the arm64 build already produced. The tests pin today's rules, including the quirks: calibration moves are never clamped or filtered but are refused while guiding is disabled, recovery moves bypass the clamp and the Dec guide mode, and the limit alert fires on the 6th clamped step in a row in one direction. A closed-loop test calibrates a planar mount model and guides through the real `calibration_transform.cpp` and `PlanOffset`/`PlanAxis`: a displaced star comes back to within 0.1 px in one step across camera angles, a mirrored Dec axis and a meridian flip with the flipped calibration, and a stale calibration after a flip is shown to drive the star away.

### Changed
- The Alpaca guide camera's `imageready` poll now backs off during the readout (#120): every 20 ms until the exposure is due, as before, then a quarter of the time waited past that, 20-250 ms, instead of every 20 ms for the whole readout (about 50 HTTP requests a second, each one a camera SDK call on some servers). A frame is seen at most 25 % of its readout, and never more than 250 ms, after it is ready; a frame ready within about 80 ms of the exposure end keeps the old cadence, and a 1 s readout takes about 20 polls instead of about 54 (a 5 s one about 36 instead of about 254). `stop_capture` during a long readout can take up to 250 ms longer. `scripts/fake_alpaca_camera.py` gains `--readout-ms` to reproduce a readout without hardware.
- `get_guide_history` now reads its steps and stats from `GuideHistory`, a wx-free store in `src/guide_history.cpp` tested by `test_guide_history` (#132, step 2 of #115), instead of the History graph window, which is removed. Its parameters and output are unchanged: the same steps give the same JSON, including the two known quirks (`t` printed with `%g`, and `ra_dir` / `dec_dir` always `""`), since fixed (#133, see Fixed). The same guide steps, star-lost frames and dithers feed it, and `delete_profile`, a profile change (`set_profile`, `set_profile_by_name`, `create_profile`, `clone_profile`) and an image-scale change clear it, as before. `/graph/minLength`, `/graph/maxLength` and `/graph/length` are still read at startup, but the history's length can no longer be changed and the history can no longer be cleared while the guider runs: the graph's length menu, the Guide Stats length button and the two Clear buttons were the only ways, and no RPC offers them. With a fresh config, the file `export_config_settings` writes no longer has `/graph/minHeight`, `/graph/maxHeight`, `/graph/RAColor` or `/graph/DecColor`, which the graph wrote at every startup and nothing reads now; its result and file name are unchanged. A saved `/perspective` that still names the removed panes is harmless (the missing panes are skipped).
- The per-frame math of the Hysteresis and ResistSwitch guide algorithms (the RA and Dec defaults) moved into the wx-free `src/guide_algorithm_kernels.{h,cpp}` (#142), with no change to guiding. `GuideAlgorithmHysteresis::result()` and `GuideAlgorithmResistSwitch::result()` call the kernel with the same arithmetic in the same order and write the same Debug lines in the same order from what it returns; the profile, the setters' checks and the dialogs stay in the classes. ### Fixed
- The `/api/frame.jpg` `ETag` changes with every new image, so a new frame no longer answers `304 Not Modified` (#259). The `ETag` `"f<N>"` was the frame counter, which goes back to 0 at every capture start and at guiding start, so the first frame of every single-frame capture was `"f1"`, and a client holding the last capture's `ETag` got `304` for a new exposure (and the same after a loop or guiding restart). N is now an id each image gets when it is made, from a per-process sequence that never resets, so it is new for every image the daemon holds, across captures and restarts of looping and guiding; the `"f<N>"` format, `304` on a matching `If-None-Match` for the same frame, and every frame number reported over JSON-RPC and in events are unchanged. Ara is not affected today: it fetches the frame with a plain GET, without `If-None-Match`. The N2 scenario in `scripts/e2e_guide_scenarios.py` now requires a `200` with a new, higher `ETag` for the next single frame, a `304` to its own, and the looping frames' `ETag`s above both.
- The HTTP data port no longer reads freed memory on every request (#258). A new connection queues a `wxSOCKET_OUTPUT` event (the socket is writable) as well as the `wxSOCKET_INPUT` one, and `EventServer::OnHttpServerClientEvent` answered the request on the INPUT event and destroyed the one-shot client, freeing its `HttpClientData`; the OUTPUT event still queued for it then read that `HttpClientData` in `flush_http_pending`. Every `/api/frame.jpg` poll from Ara's live view and polar alignment and every `/api/capture` fetch did it: a silent read of freed memory in the release `.deb`, and an AddressSanitizer abort on the first request in the sanitizer build. `wxSocketBase::Destroy()` keeps the socket object until its queued events are handled, so the handler now ignores any event for a socket that is no longer in `m_httpServerClients` (a queued `wxSOCKET_LOST` after the close no longer destroys the client a second time either). The N2 scenarios in `scripts/e2e_guide_scenarios.py` now send each request at once after the connect, as every HTTP client does, instead of 0.5 s later, so the main lane catches a regression.
- `guide` after a binning change calibrates before it guides (#255). With `recalibrate: false` on a calibrated mount, the guider decided there was nothing to calibrate, and only then, on entering guiding, did `Mount::AdjustCalibrationForScopePointing` see the new binning, raise the "Binning or camera pixel size changed unexpectedly" Alert and clear the calibration (`MyFrame::HandleImageScaleChange`); guiding started anyway, so the events were `Alert`, `StartGuiding`, `SettleBegin`, `SettleDone` (`Status` 0) with `get_calibrated` false, and only the next `guide` calibrated. The guider now checks the calibration after that adjustment and goes back to calibrating when it was cleared, and the `guide` request waits for that calibration before it settles: `Alert`, `StartCalibration` ... `CalibrationComplete`, `StartGuiding`, `SettleBegin`, `SettleDone`. A headless Guiding Assistant run that started guiding (its guide output is off, so it cannot calibrate) fails with a message saying so instead of measuring on a cleared calibration. The gear lane's "binning change on guide start (#115 N4)" scenario now expects the calibration in the same `guide`.
- A step of the system clock no longer ends a guide or dither settle early or holds it (#257). `PhdController` timed the settle timeout and the run of in-range frames with `wxStopWatch`, which reads the wall clock; RC51 boots with a stale clock and then syncs it, so a step forward settled an in-range run on the next frame (Ara opened a sub before the guider had settled) or, with no run under way, timed the settle out on the next frame and failed the dither, and a step back held both, with a negative `Settling` `Time`, until the step had passed in real time. `SettleTracker` now reads #231's `monotonic_timers::ClockMs`, the same `steady_clock` as the other guider timers; `test_settle_tracker` covers it with ±1 h steps and checks the clock it reads. No JSON-RPC or event change: `Settling` `Time` is still the seconds in range and `SettleDone` is sent once per settle as before; the guide log's settling lines carry no times.
- Auto-select no longer picks a star one pixel too close to the right or bottom edge (#142). `GuideStar::AutoFind` dropped peaks at `x >= width - edgeDist` (the search region plus the edge allowance, and the same for y), while `GuiderMultiStar::IsValidLockPosition` wants `x + 1 + searchRegion < width`, so with no allowance (a calibrated mount, `find_star`, `get_star_centroids`) it could choose a star at `x = width - searchRegion - 1` that the guider's own lock-position check rejects: with a lock-position shift on, a shift that did not move it inward raised `LockPositionShiftLimitReached` at once and turned the shift off. AutoFind now uses `ClearOfEdge` from `src/edge_allowance.cpp`, which needs that pixel more on the right and bottom and, with no allowance, keeps exactly the positions `IsValidLockPosition` (now `ValidLockPosition` in the same file) accepts. A star already selected is checked for a forced recalibration by the same rule. Covered by `test_edge_allowance`.
- `star_find::FindStar` no longer reports a star found when its background annulus has 1-9 pixels (#142). The 7-12 px annulus around the peak gives the background mean and noise; with fewer than 10 of its pixels in the frame on the first pass, the loop stopped with both still 0, so the threshold was 0, the sky counted as star (mass 28706 for a star of 18850 in a 10 px frame), the SNR was inflated and the centroid pulled toward the frame centre, and the result was Ok. It is now not found (LowSNR), as for an empty annulus. Only a frame or subframe under about 12 px across has such an annulus, so the guider's frames (a subframe is at least 15 px, a search region at least 7) were not affected. Covered by `test_star_find_synthetic`.
- Dec backlash compensation no longer adds false reversal pulses in a North- or South-only Dec guide mode (#142). `Scope::SetDecGuideMode` turns the compensation off for North, South and Off ("no recovery from over-shoots"), but `set_backlash_comp` with `Enabled: true`, a Guiding Assistant apply or a profile can turn it on in those modes. It then counted the guide steps the mode filters out: each South request the mode dropped set the last Dec direction to South, so the next North pulse was taken for a reversal and got the whole compensation pulse more (four 100 ms North steps among alternating requests sent 2800 ms with an 800 ms compensation). The compensation now acts only while the Dec guide mode is Auto; in the other modes it adds nothing and leaves the last direction alone. The JSON-RPC API does not change: `set_backlash_comp` takes and stores `Enabled` as before and `get_backlash_comp` reads it back, and the stored setting acts once the mode is Auto again. The reversal decision moved from `BacklashComp::ApplyBacklashComp` into the wx-free `guide_move_plan::PlanBacklashComp`, covered by `test_guide_move_plan`.
- The recommended calibration step is no longer computed from an unknown image scale or guide speed (#142). `CalstepDialog::GetCalibrationStepSize`, which `Scope::CheckCalibrationDuration` runs on a binning or guide-speed change and `AdvancedDialog::MakeImageScaleAdjustments` on an image-scale change, divided by the focal length, so a profile with focal length 0 (the default, which `set_profile_setup` accepts) gave an infinite image scale and converted infinity to an int, which is undefined behaviour; a pixel size of 0 did the same to the calibration distance, and a guide speed of 0 to the step. The math moved, with the same arithmetic in the same order, into the wx-free `src/calstep_math.{h,cpp}`, which now keeps the 25 px distance and leaves the calibration duration as it is (with a debug line) when the focal length, pixel size, binning or guide speed is not above 0, or the step is not a positive number of ms an int holds. Covered by `test_calstep_math`: golden values (FL 400 mm at 3.75 µm: 1.934"/px, 25 px and 550 ms at 0.5x on the equator, 1100 ms at Dec 60) and a differential against a frozen copy of the old lines.

- The config file can no longer be left empty or missing by a power cut while it is written (#142). `PhdConfig::Flush` used `wxFileConfig::Flush`, which writes a temporary file and renames it over the config without an fsync of either, and before wxWidgets 3.2.8 (Ubuntu 24.04 has 3.2.4, Raspberry Pi OS bookworm 3.2.2) deletes the config before that rename. Before the Dec leg, clearing pulses North until three pulses in a row each move the star at least 0.6 of a pulse's expected move, and it took that move from the RA rate the West leg measured. The RA rate shrinks with cos(Dec) while a Dec pulse moves the star as far at every Dec, so the move it looked for shrank toward the pole: 1.3 px at the equator on the FL 400 mm / 3.75 µm / 0.5x profile, 0.2 px at Dec 80°, which #141 lets a calibration reach. Noise between two frames passed for a 0.2 px move, so clearing could end with backlash left, and the North leg then measured it into the Dec rate: in a sim at Dec 80° with 2500 ms of Dec backlash and 0.2 px of noise, every one of 20 seeds accepted a move while the backlash still took the whole pulse, and 5 measured the Dec rate 3-17 % low. With the Dec the guider reads at the start of the calibration, clearing now expects the Dec leg's move at every Dec: the RA rate divided by cos(Dec) (|cos| at least 0.01, so a reading at the pole stays finite), times the Dec/RA guide-rate ratio as before. With no Dec from the mount it is as before, so the calibration matches the frozen twin exactly. There is no cap: a move larger than the mount makes only means none is accepted, and clearing goes on once the star has moved the calibration distance, as for any mount whose moves are too small; a mount that reports 85° while it points at the equator does that and completes with the true Dec rate. That has a cost a client can see. A reading whose cos(Dec) is under 0.6 of the true one is enough, 55° reported at the equator already, and so is a mount in a false Home that reports Dec 90°: clearing then uses up the calibration distance going North before the North leg starts, so the star travels about twice the calibration distance North (51.8 px against 30.4 px with the right reading in the sim, for a 25 px calibration distance), more than the edge margin auto-select keeps (#140, the calibration distance plus the search region), and a star picked near that margin can leave the frame. The South leg only sends back the North leg's pulses and the nudge is at most 4 pulses of one step, so the star ends about one calibration distance from the lock (23.5 px instead of about 2 px) and guiding then has to bring it back. Tested in `test_closed_loop_calibration` (`test_high_dec_calibration.cpp`): the step helper over Dec, unknown and non-finite Decs and the pole, the Debug line's 1.3 px at Dec 0°, 60°, 80°, 85° and −80°, the guide-rate ratio, the 20 noisy seeds at 80° (no move accepted while the backlash takes the pulse, the Dec rate within 3 % below and 5 % above), and wrong readings of 55°, 60°, 85° and 90° at the equator, with the star's furthest point and where it ends.
- The max-duration alert ("PHD2 is not able to make sufficient corrections in RA/Dec...", an `Alert` event) now comes one guide step earlier: on the 5th guide step in a row clamped to the max RA or Dec duration in the same direction, as `LIMIT_REACHED_WARN_COUNT` (5) intends, instead of the 6th (#153). The first clamp of a run only recorded the direction and left the count at 0, so it reached 5 a step late. What starts a new run is unchanged: a clamp in the other direction (now counted as the first of its run), a step that is not clamped, or one the Dec guide mode zeroes; moves that are not guide steps still leave the count alone, and the alert is still shown at most every 30 s. Tested in `test_guide_move_plan`, whose pin of the 6th-step alert is now `FifthClampInARowInOneDirectionRaisesTheAlert`.
- `scripts/phd2_rpc_smoke.py` passes again on the API-only daemon (#155). It failed 12 checks on `main` that had nothing to do with the change under test, so it could not catch a real regression. It now checks that the removed INDI methods (`get_indi_server`, `set_indi_server`, `get_selected_indi_mount_driver`, `set_selected_indi_mount_driver`, `get_selected_indi_camera_driver`, `set_selected_indi_camera_driver`) answer `-32601`; that `get_selected_aux_mount` and `get_selected_ao` read "None" and their setters are refused with error 1 "not supported"; that `get_equipment_choices` lists `camera`, `mount` and `rotator` and no `aux_mount` or `AO`; that `set_alpaca_server` writes back the profile's values, leaving out the port 0 of a profile with no Alpaca server, which is refused with `-32602`; and that `query_alpaca_devices` fails with error 1 on such a profile, refuses port 0 and an unknown device type with `-32602`, and, with `--fake-alpaca-url`, lists the camera and telescope of `scripts/fake_alpaca_camera.py`, which now answers `GET /management/v1/configureddevices` for it.
- A random dither no longer repeats the same offsets on every start of the guider (#173). `MyFrame::Dither` drew them from `rand()`, which only the simulator camera ever seeded, so with an Alpaca camera each start began from the C library's default state: the first 3 px dither after a start was always RA +2.04, Dec −0.63 px, and every night repeated the last night's pattern. Random dither now has its own `std::mt19937`, seeded once at startup from `std::random_device` with the clock mixed in, in the wx-free `src/dither_random.cpp` (tested by `test_dither_random`). The offsets keep the old distribution: RA, and Dec unless the dither is RA only, each uniform over [−amount, +amount] with both ends included. Spiral dither, which uses no random numbers, and the simulator camera's own `rand()` use are unchanged. The e2e physics lane's dither check, which always saw the same dither before, now also allows for `get_lock_position`'s 0.01 px rounding, which matters for a dither well under a pixel.
- The max-duration alert ("PHD2 is not able to make sufficient corrections in RA/Dec...", an `Alert` event) is now throttled per axis, and only an alert actually raised starts its 30 s (#164). `Scope::AlertLimitReached` used one function-static time for both axes and every mount, so an RA alert held a Dec alert back for 30 s and the other way round. It also restarted that time before it checked the 120 s grace period after a calibration or a guide start, so a clamped guide step during the grace period, which raises nothing, held the first alert after the grace period back for up to 30 s more. Each axis now has its own 30 s, kept on the mount, a call that raises nothing leaves it alone, and the grace period, the alert texts and the 5-step count are unchanged. The decision is in the wx-free `guide_move_plan` (`LimitAlertThrottle`), tested in `test_guide_move_plan`: an RA alert does not hold back a Dec one or the other way round, a held call does not extend the throttle, and neither a call nor a run of guide steps during the grace period holds back the first alert after it.
- The max-duration alert's 30 s throttle and the 120 s grace period after a calibration or a guide start now run on the monotonic clock instead of the wall clock (#212). `Scope::AlertLimitReached` and `Scope::DeferPulseLimitAlertCheck` read `wxDateTime::GetTimeNow()`, so when the system time was stepped (RC51 boots with a stale clock and then syncs it) a step back held the next alert back for as long as the step, and a step forward ended the grace period early. Both now read `guide_move_plan::AlertClockS` (`std::chrono::steady_clock`, whole seconds), tested in `test_guide_move_plan`; the throttle, the grace period and the alert texts are otherwise unchanged.
- A dither's fast recenter now counts only what the mount moved (#165). After a dither the guider moves the star back in large recovery steps that bypass the guide algorithm, and it took each step off the distance left whatever happened to it, so a step `Scope::MoveAxis` cut to the 25 s pulse ceiling (#152), an AO step cut at the AO's travel, or a step that failed or was refused (guiding disabled) counted as done. The recenter then ended short of the dither and the guide algorithm, held to the max RA/Dec duration, had the rest to correct; with guiding disabled it went on sending refused steps until it had counted the whole dither. `Mount::MoveOffset` now records what each axis moved, from the pulse it asked `MoveAxis` for (with any Dec backlash compensation, which is taken up first) and the `amountMoved` it got back, and the move-complete event hands it to the guider, which takes that off the distance left when the step's move completes instead of when it is sent. A cut step is made up by another step, and so is a step that moved nothing, such as one that hit a one-off pulse error; three steps in a row that moved nothing (`RECENTER_MAX_STALLED_STEPS`), as when guiding is disabled, end the recenter, so the guide algorithm takes over instead of the same step being sent every frame. When every pulse is sent whole, as on a normal mount, the recenter takes the same steps as before, and the variable exposure delay still counts a frame as recentering up to the step that moves the rest of the dither, not the frame after it; the guider decides that when it sends the step, not when the step's move completes, since the worker thread may already be starting the next exposure then. Not changed: recenter steps still ignore the Dec guide mode, Off included, and still are not held to the max RA/Dec duration (pinned in `RecoveryAndBumpMovesIgnoreTheDecGuideMode`, #162). The arithmetic is in the wx-free `guide_move_plan` (`MovedPx`, `AfterRecenterStep`), tested in `test_guide_move_plan`: a cut, failed, AO-cut and backlash-compensated step, and recenters run through `PlanOffset` and `PlanAxis` in which a cut step is made up by a third step, a step that fails once is made up by the next ones, and refused steps end the recenter after three in a row.
- The variable exposure delay is now decided on the main thread (#182). `MyFrame::GetExposureDelay` ran on the worker thread at the start of each exposure and read `Guider::IsGuiding()`, `PhdController::IsIdle()`, `Guider::IsRecentering()`, `Mount::GetGuidingEnabled()`, the time lapse and the variable-delay settings, all written on the main thread (the settings by `set_variable_delay_settings`), with nothing ordering the two threads. `MyFrame::ScheduleExposure` now decides the delay when it queues the exposure, after the previous frame has updated the guide and controller state, and the worker sleeps the delay that came with the request. The rule is unchanged: the long delay only while guiding steadily, the short one while recentering after a dither, settling, looping or calibrating, or with guide output disabled, and the time lapse with the variable delay off. It is in the wx-free `variable_delay.cpp` (`VariableDelay::ForNextFrame`), tested in `test_variable_delay`. The only difference a client could see: a request that changes that state (a `dither`, `set_variable_delay_settings`) while the worker is still sending the guide pulse queued ahead of an exposure now takes effect from the frame after it, as it already did whenever it arrived during the delay or the exposure.
- The "PulseGuide command to mount has failed" alert (an `Alert` event) is now raised at most once every 30 s per mount (#188). `ScopeAlpaca::Guide` raised it for every pulse that failed, so a mount that stops taking pulses sent Ara two identical `Alert`s a frame when both axes corrected (12 for 6 `GuideStep`s). The first failed pulse still raises it at once, then the next one is raised 30 s after it at the earliest (timed to the whole second), whichever axis failed, timed on a steady clock so a system clock step does not hold it back. The alert text, its "don't show again" setting, the failed move and guiding going on are unchanged. The decision is in the wx-free `guide_move_plan` (`PulseFailedAlertThrottle`), tested in `test_guide_move_plan`, and the faults lane of the daemon e2e run now requires the `Alert`s to be about 30 s apart (more than 29 s).
- The event server no longer casts each accepted client socket to `wxSocketClient` (#209). `wxSocketServer::Accept` returns a plain `wxSocketBase`, so the JSON-RPC (:4400) and HTTP servers' `static_cast` on every connect, inherited from PHD2, was undefined behaviour; it worked only because nothing called a `wxSocketClient` member on it. The servers now hold their clients as `wxSocketBase`, which has every call they make. Nothing changes on the wire. The CI ASan/UBSan build of the e2e daemon now has the UBSan vptr check on in every file, which reported that cast at the first connect of every lane before this fix, so the next bad downcast fails CI. It was left out before because of the null `pFrame` member calls fixed in #168, which GCC's vptr check crashed on.
- The e2e faults lane no longer fails, now and then, on where the fake-killed scenario's kill lands (#211). `scenario_fake_killed` stopped the fake Alpaca server at whatever moment the guider was at: a kill between two camera calls makes the next call a refused connection, which reconnects the camera (#190), and a kill while a call waits on the server (most often `startexposure` on a loaded machine) fails that call with "no response from the Alpaca server" instead, which stops guiding with no reconnect, so the scenario's checks failed whenever the kill landed the other way, and it then returned with the fake still stopped, failing the reconnect throttle and GA exit restore scenarios after it too. The lane now runs both cases on purpose, as two scenarios. Between calls: the fake holds an `imageready` and closes its listening socket meanwhile (the new `/fake/stop_listening`), so that call is answered and the next one is refused, and the scenario pins #190's sequence and the #104 reconnect when the fake is back. Mid-request (`scenario_fake_killed_mid_request`): the fake is killed while a `startexposure` waits on it (`/fake/stall` takes a `call=` that stalls only that endpoint), and the scenario pins today's behaviour, an `Alert`, guiding stopped and the camera still connected (#237 asks whether that should reconnect too), then guide settles once the fake is back. The lane starts the fake again when either fails without it. Test-only; the guider is unchanged.
- The noise reduction a frame is filtered with is now read on the main thread (#210). `WorkerThread::HandleExpose` read `MyFrame::GetNoiseReductionMethod()` on the worker thread after each capture, while `set_noise_reduction` writes it on the main thread, with nothing ordering the two threads. `MyFrame::ScheduleExposure` now reads it when it queues the exposure and the worker applies the method that came with the request, as #182 did for the exposure delay. The difference a client can see: a `set_noise_reduction` that arrives while a frame is being exposed now takes effect from the next frame; before, the frame in flight was filtered with the new method. `get_noise_reduction` and the saved profile setting change at once, as before. Pinned by a main-lane scenario in `scripts/e2e_guide_scenarios.py`.
- A camera binning change that is not a whole multiple of the calibration's (2 → 3, 3 → 4) is now seen as an image-scale change when guiding starts on that calibration (#252). The rescale of a calibration taken at another binning multiplied the image-scale ratio by `binning / calibration binning` in integer arithmetic, so 2 → 3 gave 1 instead of 1.5 and `HandleImageScaleChange` did not run: the calibration step and min-move stayed sized for the old binning, the guide history and the calibration were not cleared, and there was no alert. The factor is now the exact ratio, in `calibration_adjust::AdjustForBinning`; the rates were already rescaled with it. A change to a smaller binning (3 → 2, 2 → 1) gave 0 and was handled only by accident; it now gives 2/3 and 0.5, with the same result. `test_calibration_adapt` asserts 1.5 for 2 → 3 and the exact factor for the other combinations.

- Web app live view could show a stale frame and leak a blob URL: `refreshFrame` cleared its `frameBusy` re-entrancy guard in the `finally` block, which runs before the off-screen probe `Image` finishes decoding, so the next 400 ms poll tick could overlap and race two probes — the later-decoding one would win, displaying an older frame and orphaning the newer frame's `URL.createObjectURL` allocation. The guard is now held until the probe resolves (`onload`/`onerror`), and the `onerror` path revokes the URL it would otherwise leak. Surfaced by the PR #55 review.
- The web app showed **no camera image when browsed from another machine** (fine on the guider box itself): the HTTP server wrote responses with a single non-blocking send and *dropped whatever didn't fit in the kernel socket buffer* (~140 KB over a real NIC — every ~1.2 MB frame JPEG was truncated; tiny JSON responses always fit, so the rest of the UI worked, masking the cause). Loopback's effectively unbounded buffers meant local browsing never hit it. Responses that don't fit are now queued per-client and drained on socket-writable events, with the one-shot connection close deferred until the queue empties. Verified with a deliberately slow 8 KB-receive-window client: full byte-exact JPEG delivered (previously ~145 KB of 1.2 MB).
- Web app live view lagged the camera by up to ~2.5 s while looping — the frame was only refetched on the 1.2 s main poll tick. The frame now polls on its own 400 ms timer, and `GET /api/frame.jpg` carries an `ETag` derived from the guider's frame counter so unchanged frames answer `304` without re-encoding the JPEG; the view updates within ~0.4 s of each new frame. - `GPTest.drawSamples_prior_covariance_test` was flaky — the test draws 20 000 samples and compares empirical to analytical covariance within a 2e-1 tolerance, but Eigen's `setRandom()` (used by `math_tools::generate_normal_random_matrix`) reads from `std::rand()`, so run-to-run variation occasionally pushed the empirical covariance outside the band. The `GPTest` fixture constructor now seeds `std::srand(1)`, making every statistical-expectation test in the fixture reproducible across runs. Test-only change. Fixes #8.
- `GPTest.drawSamples_prior_covariance_test` then failed deterministically on the Debian build (passed on Windows/macOS) after the srand seed went in. `std::rand()`'s sequence is platform-specific (glibc vs MSVCRT vs BSD libc), so seed 1 yields a different Monte Carlo realization on each platform; with N=20000 samples the empirical-covariance SE is ~0.15 and the 2e-1 tolerance was only ~1.35σ wide, which glibc's draw happened to land just outside (15.004 vs 14.778, diff 0.226). Loosened the tolerance to 5e-1 (~3.4σ) so the test stays meaningful while tolerating cross-platform `std::rand()` differences under the fixed seed. Test-only change.
- `build-exe.ps1` failed to parse on Windows PowerShell 5.1 after the test-gate commit (94c80630). Two em-dashes (U+2014) were added to a comment and a `Write-Error` string; PS 5.1 reads UTF-8-without-BOM `.ps1` files as CP1252, where the em-dash's UTF-8 bytes (`E2 80 94`) decode to a trailing right-curly-quote that the parser treats as a premature string terminator, producing misleading "missing closing '}'" errors pointing at unrelated lines downstream. Replaced both em-dashes with ASCII hyphens. PowerShell 7+ wouldn't have hit this because it defaults to UTF-8.
- `build-exe.ps1` aborted with `CTest not found at 'ctest.exe'` even when `ctest` was on `PATH`. `Get-Command ctest` returns a `CommandInfo` object whose default string form is just the command's `.Name`; the script then called `Test-Path` on that, which looked for a literal `ctest.exe` in the current directory. Now extracts `.Source` when `Get-Command` succeeds so `Test-Path` and the invocation see the resolved full path.
- `build-exe.ps1` packaging step aborted with `Source file ... msvcr120.dll does not exist`. `phd2.iss.in` still listed `msvcr120.dll` — the **Visual C++ 2013** C runtime — but the fork builds with VS 2022, which produces the VC 14.x runtime (`vcruntime140.dll` / `msvcp140.dll`) instead. - Test binaries on Windows failed to compile with `Cannot open include file: 'phd_version.h'`. `tests/CMakeLists.txt` set `target_compile_options(... -include <shadow phd.h>)`, which is GCC/Clang force-include syntax; MSVC silently emits warning D9002 and ignores it, so the shadow header was never active and the real `src/phd.h` won normal lookup (and pulled in `phd_version.h`, generated only into the main build target's include path). Branched on `MSVC` to emit `/FI<file>` instead, which is MSVC's force-include flag.
- Linux desktop launcher did nothing on a fresh install. `phd2.desktop` referenced the pre-rename binary name (`Exec=phd2`, `Icon=phd2`, `StartupWMClass=phd2.bin`), all of which became invalid when `debian/rules` renamed the installed binary to `openastro-phd2` / `openastro-phd2.bin`. Renamed the file to `openastro-phd2.desktop`, updated all three fields, and renamed `phd2.appdata.xml` → `openastro-phd2.appdata.xml` (plus its internal `<id>` and `<launchable>` AppStream refs) so GNOME Software / KDE Discover index us under the new app id. `cmake_modules/PHD2Packaging.cmake` install paths now drop `/usr/share/applications/openastro-phd2.desktop`, `/usr/share/pixmaps/openastro-phd2.png`, and `/usr/share/metainfo/openastro-phd2.appdata.xml` so the desktop file's `Icon=openastro-phd2` resolves via XDG icon theme lookup.
- Could not run OpenAstro PHD2 and upstream PHD2 simultaneously on Windows. The second app to launch hit `wxLogError("PHD2 instance 1 is already running")` even though their wxApp `AppName` values are distinct (`OpenAstroPHD2` vs `PHD2`). Root cause: `src/phd.cpp` constructed the `wxSingleInstanceChecker` lock *before* calling `SetAppName()`, so `GetAppName()` fell back to the executable basename — and on Windows the .exe is still `phd2.exe` in both apps (we relocate it under `OpenAstroPHD2\` at install time, the file itself keeps its short name). Both apps therefore took a lock named `"phd2.1"` and collided. Reordered so `SetVendorName` / `SetAppName` run first; the lock is now named `"OpenAstroPHD2.1"` on Windows/macOS and `"openastro-phd2.1"` on Linux — distinct from upstream's `"phd2.1"` / `"PHD2.1"` on every platform.
- `build-dmg.sh` failed on macOS Tahoe with `text: command not found` followed by `Finder got an error: Can't get disk "PHD2" (-1728)`. The first error was bash interpreting backticks in an AppleScript comment (`` `text color` ``) as command substitution inside the unquoted heredoc, replacing them with empty strings — noisy but non-fatal. The second was the real failure: `hdiutil attach` returns once the kernel mount lands, but Finder only learns about the volume asynchronously via diskarbitrationd, and on Tahoe the gap between mount and Finder-readiness is long enough that the immediately-following `tell disk "PHD2"` raised -1728. Both fixed: the comment now uses quoted text instead of backticks, and the script polls `/Volumes/PHD2` for up to 5 s before talking to Finder (plus a 1 s `delay` at the top of the AppleScript for belt-and-suspenders).
- `debian/openastro-phd2.postrm` removes `/var/lib/openastro-phd2` on package purge. The postinst creates this directory for runtime state (calibration, profiles, logs); Debian policy requires purge to delete all package state. Without this, `apt purge openastro-phd2` would leave the state dir orphaned on disk.
- `test_jsonrpc_schema.cpp` now type-guards every `json_value` union access. Added `ASSERT_EQ(units->type, JSON_STRING)` and `ASSERT_EQ(axes->type, JSON_STRING)` before the `string_value` reads in the `GetLockShiftParams` enabled branch, and upgraded the `expect_string_field` / `expect_numeric_field` / `expect_bool_field` helpers from `EXPECT_EQ` to `ASSERT_EQ` on the type check. Wrong-type accesses now hard-stop the test instead of progressing to UB on a mismatched union member.
- `test_jsonrpc_schema::JsonRpcSchema.SettleDoneEvent` now asserts `Error` is absent on success (Status==0) responses, not just on the failure branch. Schema spec says Error exists iff Status≠0; downstream consumers (NINA, KStars) read `Error` as a truthy "did the settle fail" indicator, so a spurious empty-string Error on success would look like a settle failure to them.
- `test_jsonrpc_schema::JsonRpcSchema.ResponseEnvelopeSuccess` and `ResponseEnvelopeError` now assert envelope exclusivity (`result` xor `error`). Previously each branch only asserted the required key was present; a mixed envelope with both keys would pass both tests silently. Per JSON-RPC 2.0 the response MUST have exactly one of `result` or `error`.
- `test_jsonrpc_schema::JsonRpcSchema.GetLockShiftParams` disabled-branch now asserts `rate`, `units`, and `axes` are absent. Comment said "only enabled is present" but the test didn't enforce it; a server that started emitting `rate`/`units`/`axes` alongside `enabled=false` would pass the test.
- `build-dmg.sh` shipped a DMG that crashed on launch with `Library not loaded: /opt/homebrew/...libcfitsio.10.dylib` on any Mac without Homebrew installed at the same prefix as the build host. `bundle_app_dylibs` and `check_library_dependencies` both hardcoded the binary path as `Contents/MacOS/PHD2`, but the same release renamed CMake's `OUTPUT_NAME` to `"OpenAstro PHD2"` so the binary actually lives at `Contents/MacOS/OpenAstro PHD2`. `otool -L` against the missing PHD2 file produced empty output, which silently skipped both the dylib bundling step AND the safety-net check that exists specifically to fail-loud on unbundled `/opt/homebrew/...` loads. End result: the DMG appeared to build cleanly, ran fine on the developer's Homebrew-equipped Mac, and crashed at launch on the user's. Both helpers now use a new `APP_EXE` variable defined alongside `APP_BUNDLE` (so they move in lockstep with CMake's OUTPUT_NAME), and added an `[[ -f "$exe" ]] || err …` guard so any future drift fails the build instead of shipping a Homebrew-coupled binary.

<summary><strong>[1.3.0] - 2026-05-12</strong></summary>

### Fixed
- **Alpaca discovery misses loopback-bound servers**
  - `AlpacaDiscovery::BuildBroadcastTargets()` now always probes `127.0.0.1:32227` as a unicast target so Alpaca servers bound only to loopback (e.g. ASCOM Remote Server's default "Loopback" IP setting) are discovered. Previously these were invisible because subnet broadcasts (255.255.255.255 and per-interface broadcasts) never reach loopback-only listeners — the workaround was to manually edit Remote Server to bind to the LAN IP.
  - Added Linux/macOS network-interface enumeration via `getifaddrs`. Previously the non-Windows path sent only to `255.255.255.255`, so multi-NIC Linux/Pi setups (VPN, docker, multiple LANs) missed servers on subnets the default route did not cover. Mirrors the Windows `GetAdaptersAddresses` path and the pattern in `indi_discovery.cpp`.

### Removed
- **`PHD2_ALLOW_INDI_1_9` escape hatch dropped**
  - INDI 2.0+ is now a hard requirement. Removed the option from `thirdparty/thirdparty.cmake`, the env-var plumbing in `run_deb.sh` / `build-deb.sh`, and the `PHD2_ALLOW_INDI_1_9` make variable in `debian/rules`. The Player One driver and several other INDI drivers have meaningful fixes after 1.9.x; keeping the toggle invited subtly broken builds.
  - For Debian/Pi systems that only ship INDI 1.9.x, `run_deb.sh` now auto-detects this and falls back to building INDI 2.1.6 from source — no manual PPA setup required.

### Changed
- **Auto-detect libindi version in all build paths**
  - `run_deb.sh`, `debian/rules`, and `build-deb.sh` now all probe `pkg-config --atleast-version=2.0.0 libindi`. When the system libindi is missing or < 2.0.0, the build sets `USE_SYSTEM_LIBINDI=0` so CMake fetches and builds INDI 2.1.6 from source as a static client library (no shared libs to bundle). The from-source path was already wired into `thirdparty/thirdparty.cmake`; it just wasn't reachable from any of the user-facing scripts. Override with `USE_SYSTEM_LIBINDI=0` or `=1` explicitly.
  - `build-deb.sh` no longer hard-fails on stale libindi-dev: it now prints which path will be taken (system or from-source) and proceeds. Older libindi-dev on Debian trixie / Pi OS no longer blocks `.deb` builds.
- **Alpaca port default is now `0` (unconfigured) instead of `6800`**
  - `pConfig->Profile.GetLong("/alpaca/port", ...)` now defaults to `0` in `cam_alpaca.cpp`, `scope_alpaca.cpp`, `rotator_alpaca.cpp`, `camera.cpp`, `scope.cpp`, `rotator.cpp`, and `event_server.cpp`. The previous `6800` was AlpacaBridge-specific and misleading for users running ASCOM Remote Server (default `11111`) or anything else.
  - `Connect()` "not yet configured" sentinel in the Alpaca camera/mount/rotator drivers simplified from `host == "localhost" && port == 6800 && device == 0` to just `port == 0`. The old triple-check could spuriously re-open the setup dialog for users genuinely running AlpacaBridge at `localhost:6800` with device 0.
  - `AlpacaConfig::SetSettings()` renders an unconfigured port as an empty field instead of literal `"0"`. The dialog's existing auto-discover path fires when the server list is empty, so new profiles open with empty fields and discovery immediately populates them — matching NINA's flow.
